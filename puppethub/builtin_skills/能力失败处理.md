## 能力失败处理（失败必须有人接）

**这是第一原则的直接体现**：能力会失败（网络断、超时、参数错、外部服务挂），
而**没人接的失败 = 界面上毫无变化 = 用户以为还在转**。所以语言把它做成警告：
`UNCOVERED_FAILURE`（槽的 `error` / `timeout` 既没处理器也没订阅）。

### 五个槽事件，按需接

| 事件 | 什么时候触发 | 典型处理 |
|---|---|---|
| `pending` | 调用开始 | 转圈 / 改状态文案 / 禁用按钮 |
| `done` | 成功 | 显示结果 / 收起进度 |
| `error` | 能力抛异常 | **必须**：告诉用户失败了 + 为什么 |
| `timeout` | 超过时限 | 提示"超时" + 给重试入口 |
| `cancel` | 被新调用顶掉 | 通常忽略（这是正常行为，不是错） |

```puppet
on #mail pending: set #status text="正在发送…" ; set #send disabled=true
on #mail done:    set #status text="已发送" ; set #send disabled=false
on #mail error:   set #status text="发送失败：" + #mail.status ; set #send disabled=false
on #mail timeout: set #status text="超时了，点「重试」再来一次" ; set #send disabled=false
```

**关键三条**：
1. `pending` 里**禁用触发按钮**——否则用户狂点产生重复调用。
2. `error` / `timeout` 里**必须恢复按钮可用**，否则一次失败后按钮永久禁用。
3. 错误文案**给具体原因 + 出路**，不要只说"失败"（措辞纪律见 `图标与文案`）。

### 重试：靠"重新调用"，不要写循环

语言**没有循环**。重试的正确做法 = 让用户再点一次（或换个按钮）→ 再 `call` 一次：

```puppet
on #retry click: call send_mail with {to: #user.value} into #mail
```

同一槽的新调用会**自动取消旧的**（可见，非静默），所以不需要手动清理。

### 降级：失败了给退路，别留白

```puppet
add #main text #fallback text="数据没拉到，先看看缓存" fg=#dc2626 visible=false
on #feed error: set #fallback visible=true
```

优先保证界面**永远有东西可看**，而不是失败后一片空白。

### 常见诊断速查（读诊断先看这几个码）

| 诊断码 | 级别 | 含义 | 怎么修 |
|---|---|---|---|
| `CAP_NO_DOC` | 错误 | 能力没写 docstring | 补 docstring（不注册 = 界面里没有它） |
| `CAP_IMPORT` | 错误 | 能力模块导入失败 | 看报错：语法错 / 缺包 / 路径不对 |
| `CAP_DEPS_MISMATCH` | 警告 | `REQUIRES` 与实际 import 不符 | 补齐声明（防部署机缺包） |
| `CALL_UNKNOWN` | 错误 | `call` 的能力名不存在 | 拼写？还是没写进 `capabilities.py`？ |
| `CALL_CONTRACT` | 错误 | 参数名 / 类型不符契约 | 按【本 app 的能力】里的签名改 |
| `UNCOVERED_FAILURE` | 警告 | 槽失败没人接 | 加 `on #槽 error:` 处理器 |
| `SLOT_TIMEOUT` | 信息 | 槽调用超时 | 观察流里的记录（不是错误，是事实） |
| `SLOT_CANCELLED` | 信息 | 槽被新调用取消 | 正常行为，通常无需处理 |

**判据**：凡是 `错误` 级别的，**能力根本没注册或没跑起来**，先修它；
`警告` 级别的还能跑，但埋着坑（静默失败的前身）。
