## 定时与巡检（让 app 自己看表）

有些事**没有事件驱动**：数据源断更了、库存跌了、任务超时了、指标半小时没动了。
这些要靠**定时看一眼**（`every`）或**盯一个条件**（`when`）——你用 `watch` 块声明。

````
```watch
every: 5m
when: #stock.value < 10
why: 库存低于 10 要提醒
```
````

把"检查"做成**能力**、靠外部触发（用户动作 / 事件）调用，永远比定时轮询便宜——
所以**先问自己：这件事能不能被"用户做了 X"或"数据到了 Y"触发？能就别用 `watch`**。
`watch` 是给"确实没人会来、只能自己看表"的那类事用的。

```puppet
// 能事件触发就别用 watch：手动点一次，比定时轮询便宜得多
add #main button #check text="检查更新" icon=refresh
on #check click:
    call check_freshness with {source: #feed} into #fresh
    set #status text="上次更新：" + str(#fresh.value)
```

### 三种形态


| 写了什么 | 语义 |
|---|---|
| 只有 `when` | **条件驱动**：值跨过边界就唤醒（"#last_ok 超过 10 分钟没更新 → 去查"） |
| 只有 `every` | **纯定时**：到点就唤醒（"每 5 分钟巡检一次数据源还在不在"） |
| 两者都有 | **到点才求值**，条件真才唤醒（"每分钟看一次，库存低了才动"） |

### 什么时候该用，什么时候不该

| ✓ 该用 | ✗ 不该用 |
|---|---|
| 数据源断了/断更了 | 按钮点击、输入变化——那是**事件驱动**，便宜得多 |
| 值越过了某条线 | 状态一帧变好几次——用程序内的规则算，别靠定时看 |
| 长时间没动静 | 交互能触发的响应 |
| 周期性提醒 | 纯计算（求和、计数——用 `sum` / `count` 活绑定） |

**判断法**：这件事能不能被"用户做了 X"或"数据到了 Y"触发？能就别用 `watch`。

### `when` 只支持简单比较

引擎不提供任意表达式求值（`evaluate` 是内部函数），所以 `when` 只能写：

```
#地址.属性  比较符  字面量          # 例：#stock.value < 10
```

**复杂的判断写进能力**，让 `watch` 只盯着能力结果：

```puppet
// 复杂判断（比如"连续 3 次采样都在跌"）→ 写成能力
call check_regression with {series: #metrics} into #regress
```
````
```watch
when: #regress.value == true
why: 指标连跌三次，要复盘
```
````

**别把 `when` 写成小号程序**——它每次都会求值，写得越长越容易错，也越难读。

### 边界（超了会被拒，且会告诉你）

| 边界 | 值 |
|---|---|
| watch 总数 | ≤ 8 个 |
| 最小间隔 | ≥ 30s |
| 预算 | **不因为加了 watch 而变多**——它只决定"何时用预算"，不决定"有多少" |

- 想要 `every: 5s` → 会被拒（`WATCH_REJECTED`），**这不是 bug，是护栏**：
  5 秒一次会烧光步进预算。
- 想要第 9 个 watch → 会被拒。先想想有没有该合并的。

### 写下 `why`

`why` 不是装饰——它进决策流水，事后能回答"**它当时为什么觉得该醒**"。
写"数据可能断了"比写"检查"有用得多。

### 自查清单

1. 这件事真的不能被事件触发吗？（能就别用 `watch`）
2. `when` 是简单比较吗？（复杂判断挪进能力了）
3. 间隔 ≥ 30s 吗？总数 ≤ 8 吗？
4. `why` 写清楚了吗？
5. 要不要先去查那条建议里的诊断码？（很多"该定时查"的问题有现成诊断）
